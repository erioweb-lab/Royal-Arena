# Game UI/UX Overhaul

## 목적

이 스킬은 기존 게임의 화면과 조작 경험을 분석하고 개선한다.

특정 장르, 플랫폼, 엔진, 화면 비율, 디자인 스타일을 전제로 하지 않는다.
먼저 게임의 실제 특성을 파악한 다음 그에 맞는 UI/UX를 설계하고 구현한다.

적용 가능한 대상의 예:

- 액션, RPG, 전략, 퍼즐, 캐주얼, 스포츠, 레이싱, 시뮬레이션
- 카드, 보드, 타워 디펜스, 방치형, 리듬, 플랫폼 게임
- 모바일, 데스크톱, 콘솔, 웹 게임
- 2D, 3D, 픽셀아트, 로우폴리, 실사풍, 만화풍 게임

예시는 범위를 제한하지 않는다.

## 핵심 원칙

1. 게임의 재미와 핵심 조작을 우선한다.
2. 장르와 플레이 상황에 맞게 UI를 설계한다.
3. 기존 게임 규칙과 데이터 구조를 임의로 변경하지 않는다.
4. 실제 프로젝트의 기술 스택과 구조를 우선 존중한다.
5. 보기에만 좋은 화면이 아니라 실제 조작 가능한 화면을 만든다.
6. 작업은 조사 → 계획 → 구현 → 검증 → 보고 순서로 진행한다.
7. 확인한 사실, 추정, 미검증 사항을 구분한다.
8. 없는 기능과 데이터를 임의로 만들어 표시하지 않는다.
9. 기존 에셋과 디자인 정체성을 우선 활용한다.
10. 사용자가 별도로 요청하지 않은 대규모 재작성은 피한다.

---

# 1. 사용 조건

다음과 같은 요청에 이 스킬을 사용한다.

- 게임 화면이 잘리거나 겹치는 문제 수정
- HUD, 메뉴, 인벤토리, 결과 화면 개선
- 모바일 또는 다양한 화면 비율 대응
- 게임 버튼과 조작 피드백 개선
- 기존 게임의 디자인 품질 개선
- 스크린샷을 기반으로 UI 문제 분석
- 기존 프로젝트를 분석하고 화면 개선 구현
- 특정 장르에 맞는 화면 구성 제안

사용자가 특정 플랫폼, 디자인 방향, 게임 규칙 또는 변경 범위를 지정했다면
이 스킬의 일반 지침보다 사용자의 구체적인 요구사항을 우선한다.

---

# 2. 작업 시작 전 확인

## 2.1 제공 자료 파악

사용 가능한 자료를 확인한다.

- 소스 코드 또는 저장소
- 게임 실행 환경
- 스크린샷 또는 영상
- 디자인 시안
- 기존 에셋
- 사용자의 문제 설명
- 대상 기기와 조작 방식
- 테스트 도구 및 기존 테스트 코드

자료가 충분하면 추가 질문 없이 조사와 작업을 진행한다.

게임의 목적이나 대상 플랫폼처럼 중요한 정보를 확인할 수 없고,
그 정보가 구현 방향을 크게 바꾼다면 필요한 질문만 간결하게 한다.

## 2.2 프로젝트 및 기술 구조 파악

실제 프로젝트에서 다음을 조사한다.

- 게임 엔진 또는 프레임워크
- 화면 및 UI 구성 방식
- 주요 화면과 상태 전환 방식
- 렌더링 방식
- 입력 처리 방식
- 해상도 및 화면 크기 조정 방식
- 리소스와 에셋의 위치
- 저장 데이터 및 설정
- 테스트와 빌드 방법
- 기존 접근성 설정
- 배포 및 캐시 관련 설정

실제 파일명, 클래스명, 노드명, 함수명은 확인 후 사용한다.
존재하지 않는 구조를 사실처럼 가정하지 않는다.

## 2.3 게임 플레이 파악

다음 항목을 실제 게임에 맞춰 확인한다.

- 장르와 핵심 플레이 루프
- 플레이어가 가장 자주 수행하는 행동
- 플레이 중 즉시 확인해야 하는 정보
- 승리, 실패, 진행, 보상 조건
- 사용 가능한 입력 장치
- 플레이 중 화면에서 중요한 영역
- 일시 정지 또는 화면 전환이 가능한 시점
- 빠른 반응이 필요한 구간과 느긋한 구간
- 멀티플레이 또는 실시간 상태 동기화 여부

확인할 수 없는 항목은 추정으로 표시하고,
게임 규칙을 임의로 정의하지 않는다.

---

# 3. 진단

## 3.1 화면별 문제 분석

존재하는 화면을 기준으로 조사한다.

예:

- 시작 및 로비
- 캐릭터 또는 스테이지 선택
- 게임 플레이
- 일시 정지
- 인벤토리 및 장비
- 상점 및 보상
- 결과 화면
- 설정 및 도움말

프로젝트에 없는 화면을 새로 추가하는 것은 필수가 아니다.

각 화면에서 다음을 확인한다.

### 레이아웃

- 화면 밖으로 잘리는 요소
- 겹치는 텍스트와 버튼
- 의도하지 않은 빈 공간
- 불필요한 스크롤
- 정렬이 맞지 않는 요소
- 서로 다른 화면 상태가 동시에 보이는 문제
- 안전 영역 또는 노치에 가려지는 콘텐츠

### 정보 구조

- 중요한 정보가 눈에 잘 들어오는지
- 장식이 플레이 정보를 가리는지
- 같은 중요도의 요소가 일관되게 표현되는지
- 지나치게 많은 정보가 동시에 표시되는지
- 긴 문구와 큰 숫자를 처리할 수 있는지

### 조작

- 주요 행동을 쉽게 찾고 실행할 수 있는지
- 버튼 크기와 간격이 입력 장치에 적절한지
- 선택, 비활성, 성공, 실패 상태가 명확한지
- 실수로 위험한 행동을 하기 쉬운지
- 메뉴가 실제 게임 입력을 가로막거나 중복 처리하는지

### 그래픽과 스타일

- 게임의 세계관과 UI가 어울리는지
- 배경과 텍스트의 대비가 충분한지
- 에셋의 크기, 비율, 해상도가 일관적인지
- 과도한 효과가 가독성이나 성능을 해치지 않는지
- 아이콘과 용어가 일관적인지

## 3.2 문제의 원인 확인

가능한 경우 다음을 실제 코드와 실행 화면에서 확인한다.

- 고정 크기 또는 절대 위치 사용
- 잘못된 화면 상태 관리
- 부모와 자식 요소의 크기 충돌
- 카메라 또는 뷰포트 설정
- 캔버스 표시 크기와 내부 좌표의 불일치
- 이벤트 중복 등록
- 기기별 입력 차이
- 이미지의 비율 또는 해상도 문제
- UI 스케일링 및 앵커 설정 문제
- 캐시 또는 이전 빌드가 표시되는 문제

스크린샷만 보고 확인한 현상과
코드 또는 실행을 통해 확인한 원인을 구분한다.

# 4. 계획 수립

실제 수정 전에 간결한 작업 계획을 작성한다.

## 계획에 포함할 내용

1. 확인한 게임의 특징
2. 현재 화면의 핵심 문제
3. 변경 대상 화면과 범위
4. 디자인 방향
5. 화면별 레이아웃 방향
6. 조작 및 접근성 개선 방향
7. 기술적 변경 위치와 위험
8. 검증 방법
9. 변경하지 않을 기능

## 우선순위

아래 순서를 기본으로 하되 게임 특성에 맞게 조정한다.

1. 플레이 불가, 입력 오류, 화면 잘림
2. 게임 진행에 필요한 정보의 가독성
3. 버튼 및 조작의 사용성
4. 화면 간 일관성과 반응형 대응
5. 시각적 완성도와 장식

## 계획 원칙

- 사용자가 요청하지 않은 게임 규칙 변경은 계획에 넣지 않는다.
- 대규모 엔진 교체나 프레임워크 도입을 기본 해법으로 삼지 않는다.
- 특정 게임의 화면 구조를 다른 게임에 그대로 강요하지 않는다.
- 화면이 복잡하다면 필수 정보와 보조 정보를 구분한다.
- 중요한 결정을 위한 정보가 부족하면 가정을 명시한다.

---

# 5. 디자인 방향 설정

## 5.1 게임 특성에 맞추기

다음 요소를 게임에 맞춰 결정한다.

- 세계관과 분위기
- 장르와 플레이 속도
- 주 사용 연령대
- 2D 또는 3D 환경
- 화면 방향과 비율
- 입력 장치
- 필요한 정보의 양
- 게임의 기존 브랜드 및 시각적 정체성

예를 들어 빠른 액션 게임과 복잡한 전략 게임은
같은 HUD 밀도나 버튼 배치가 적합하지 않을 수 있다.

## 5.2 디자인 토큰

프로젝트 구조에 맞게 필요한 토큰을 정의하거나 정리한다.

- 주요 색상과 배경색
- 텍스트와 보조 텍스트 색상
- 성공, 경고, 실패, 선택 상태
- 글꼴과 크기 단계
- 간격 체계
- 패널과 버튼의 테두리
- 아이콘 크기
- 그림자와 강조 효과
- 애니메이션 속도와 강도

특정 색상이나 스타일을 강제하지 않는다.

## 5.3 그래픽 및 에셋

- 기존 에셋을 먼저 확인하고 재사용한다.
- 원래 비율을 유지하고 불필요한 늘림을 피한다.
- 중요한 아이콘은 배경 위에서 구분되게 한다.
- 에셋이 없으면 간단한 임시 표현을 사용할 수 있으나,
  최종 에셋처럼 가장하지 말고 보고한다.
- 외부 에셋을 사용할 경우 사용 권한과 출처를 확인한다.
- 타 게임의 로고, 캐릭터, 독점 그래픽을 무단 복제하지 않는다.
- 장식 효과는 게임 정보와 조작 영역을 가리지 않게 한다.

# 6. 화면 구성 지침

## 6.1 메뉴 및 로비

해당 게임에 존재하는 경우 다음을 고려한다.

- 게임의 정체성이 명확하게 보이는가?
- 가장 중요한 행동을 쉽게 찾을 수 있는가?
- 설정, 도움말, 선택 기능이 적절한 위계로 배치되어 있는가?
- 플레이에 필요하지 않은 화면이 빈 영역으로 남아 있지 않은가?
- 작은 화면에서도 모든 기능에 접근할 수 있는가?

## 6.2 게임 플레이 화면

- 실제 플레이 영역을 우선 확보한다.
- 중요한 HUD는 빠르게 읽을 수 있게 한다.
- 플레이어의 시야와 주요 오브젝트를 가리지 않는다.
- 자주 사용하는 조작은 접근하기 쉬운 위치에 둔다.
- 덜 중요한 정보는 상황에 따라 축소하거나 접을 수 있다.
- 적, 아군, 위험, 목표 등은 색상 외의 단서도 고려한다.
- 진행 상황과 조작 결과에 적절한 시각·음향 피드백을 준다.
- UI가 게임의 입력과 충돌하지 않도록 한다.

## 6.3 팝업 및 모달

- 화면에 맞게 표시하고 필요한 경우 내부 스크롤을 제공한다.
- 제목, 내용, 주요 행동, 보조 행동의 위계를 명확히 한다.
- 버튼이 겹치거나 잘리지 않도록 한다.
- 배경 입력 차단 여부를 해당 게임의 설계에 맞게 처리한다.
- 닫기 또는 취소가 가능한 경우 방법을 명확하게 제공한다.
- 키보드와 게임패드 사용 시 포커스 이동을 고려한다.

## 6.4 결과 및 보상 화면

해당 게임에 존재한다면:

- 실제 결과와 데이터를 정확하게 표시한다.
- 성공과 실패를 텍스트 또는 아이콘으로도 구분한다.
- 주요 성과와 보조 통계의 위계를 나눈다.
- 재시작, 다음 단계, 로비 이동 등 기존 행동을 유지한다.
- 큰 숫자와 긴 이름에서도 화면이 무너지지 않게 한다.
- 없는 점수, 통계, 보상을 임의로 추가하지 않는다.

---

# 7. 플랫폼 및 입력 방식 대응

## 7.1 모바일

- 터치 대상의 크기와 간격을 충분히 확보한다.
- 노치, 홈 인디케이터, 안전 영역을 고려한다.
- 세로 또는 가로 방향을 게임 특성에 맞게 지원한다.
- 시스템 제스처와 게임 제스처의 충돌을 확인한다.
- 화면 회전과 앱 전환 후 상태를 확인한다.
- 손가락이 중요한 정보를 가리는지 고려한다.

## 7.2 데스크톱

- 다양한 창 크기와 해상도를 고려한다.
- 마우스 호버, 클릭, 키보드 포커스를 구분한다.
- 창 크기 변경 시 화면과 입력이 정상적으로 유지되는지 확인한다.
- 작은 창에서 주요 UI가 사라지지 않게 한다.

## 7.3 게임패드 및 콘솔

프로젝트가 지원하는 경우:

- 포커스 위치와 이동 순서를 명확히 한다.
- 현재 선택된 요소가 확실히 보이게 한다.
- 확인, 취소, 뒤로 가기 동작을 일관되게 유지한다.
- 기기별 안전 영역과 화면 비율을 고려한다.

## 7.4 공통 입력 원칙

- 사용하지 않는 입력 방식을 임의로 추가하지 않는다.
- 기존에 지원하는 입력 방식은 유지한다.
- 입력 취소, 화면 전환, 포커스 상실 후 상태를 확인한다.
- 입력 장치별 안내 문구가 실제 조작과 일치해야 한다.

# 8. 기술 구현 지침

## 8.1 공통

- 기존 기술 스택과 프로젝트 구조를 먼저 따른다.
- 수정 범위와 의존 관계를 파악한 뒤 변경한다.
- 게임 로직과 화면 표현을 가능한 범위에서 구분한다.
- 화면 상태와 이벤트가 중복되지 않도록 한다.
- 기존 저장 데이터와 설정의 호환성을 확인한다.
- 불필요한 외부 라이브러리나 대규모 재작성을 피한다.
- 임시 데이터나 디버그 화면이 최종 화면에 남지 않게 한다.

## 8.2 웹 기술 사용 시

프로젝트가 HTML, CSS, JavaScript 기반인 경우에만 적용한다.

- Flexbox, Grid 또는 기존 구조에 맞는 레이아웃을 사용한다.
- 반응형 크기, 오버플로, 긴 텍스트를 처리한다.
- 모바일 안전 영역과 뷰포트 높이 변화를 고려한다.
- 버튼, 포커스, 비활성 상태를 적절히 표시한다.
- 필요한 범위에서만 터치 기본 동작을 제어한다.
- 이벤트 리스너와 애니메이션 루프의 중복을 피한다.
- 서비스 워커 또는 캐시가 있다면 변경 사항 반영 여부를 확인한다.

### Canvas 또는 좌표 기반 전장

해당 방식이 실제로 사용되는 경우:

- 논리 좌표와 화면 표시 좌표를 구분한다.
- CSS 또는 화면 크기 변경 후 입력 좌표 변환을 확인한다.
- 기기 픽셀 비율과 내부 렌더링 해상도를 구분한다.
- 드래그, 클릭, 터치 위치와 실제 상호작용 위치가 일치해야 한다.
- 게임의 충돌 판정이나 논리 좌표를 UI 변경만을 위해 임의로 바꾸지 않는다.

## 8.3 게임 엔진 사용 시

Unity, Godot, Unreal 또는 다른 엔진을 사용하는 경우:

- 실제 프로젝트의 엔진과 UI 시스템을 확인한다.
- 해당 엔진의 앵커, 컨테이너, 스케일링,
  카메라, 뷰포트 설정을 우선 활용한다.
- 엔진과 버전에 존재하지 않는 API를 추측해 사용하지 않는다.
- 씬, 프리팹, 블루프린트, 노드 또는 리소스 간 연결을 보존한다.
- 게임 실행과 빌드 방식이 깨지지 않도록 한다.

# 9. 접근성 및 사용성

게임 성격과 플랫폼을 고려하여 적용한다.

- 주요 정보를 색상만으로 구분하지 않는다.
- 텍스트와 배경의 대비를 충분히 확보한다.
- 읽기 어려울 정도로 작은 글씨를 피한다.
- 버튼의 기본, 선택, 비활성 상태를 구분한다.
- 가능한 입력 방식에서 포커스가 보이도록 한다.
- 중요한 오류와 결과를 명확한 문장으로 표시한다.
- 움직임 감소 설정이나 과도한 화면 흔들림 완화를 고려한다.
- 자막, 글자 크기, 색상 관련 설정이 이미 있다면 유지한다.
- 접근성 기능을 새로 추가할 때는 기존 설정과 충돌하지 않게 한다.

# 10. 단계별 실행

## 단계 1: 조사

- 자료와 프로젝트 구조 확인
- 게임 장르, 플랫폼, 입력 방식 확인
- 화면별 문제와 원인 파악
- 기존 기능과 변경 위험 정리

## 단계 2: 계획

- 수정 범위와 우선순위 결정
- 화면 구조와 디자인 방향 제안
- 필요한 기술적 변경과 검증 방법 정리

## 단계 3: 구현

- 가장 심각한 잘림과 입력 문제부터 수정
- 화면별 레이아웃과 정보 구조 개선
- 디자인 시스템과 상태 표현 정리
- 필요 시 입력 및 화면 전환 처리 수정
- 기존 기능과 데이터 연결 유지

## 단계 4: 검증

- 실제 실행 가능한 경우 직접 플레이
- 화면 크기, 입력 방식, 상태 전환 확인
- 수정으로 인한 회귀 문제 확인
- 오류 발견 시 수정하고 다시 검증

## 단계 5: 보고

- 실제 수정한 내용과 파일 보고
- 실행한 테스트와 결과 보고
- 미검증 사항과 남은 위험 명시

저장소 수정이 가능한 환경에서는 계획만 작성하고 끝내지 않는다.
실제 수정이 불가능하면 그 이유를 설명하고,
가능한 수준의 파일별 변경안 또는 패치를 제공한다.

# 11. 검증 기준

## 11.1 공통

- 실행 또는 빌드가 정상적으로 되는가?
- 화면 밖으로 잘리는 핵심 요소가 없는가?
- 버튼, 텍스트, 이미지가 겹치지 않는가?
- 주요 정보와 행동을 쉽게 찾을 수 있는가?
- 화면 전환이 정상적으로 동작하는가?
- 콘솔 또는 엔진 로그에 새로운 오류가 없는가?
- 기존 저장 데이터와 설정이 유지되는가?
- 실제 게임 플레이가 수정 전처럼 가능한가?

## 11.2 화면 크기

실제 대상 플랫폼과 게임의 지원 범위에 맞춰 확인한다.

- 가장 작은 지원 화면
- 일반적인 대표 화면
- 큰 화면
- 지원하는 화면 방향
- 지원하는 최소 및 최대 창 크기
- 필요 시 다양한 화면 비율과 안전 영역

지원하지 않는 방향이나 기기까지 무조건 대응했다고 가정하지 않는다.

## 11.3 입력 및 상태

실제 지원하는 항목만 검증한다.

- 마우스 클릭 및 드래그
- 터치 및 드래그
- 키보드
- 게임패드
- 선택, 취소, 뒤로 가기
- 일시 정지 및 재개
- 재시작 및 화면 이동
- 창 크기 변경 또는 화면 회전
- 앱 전환 및 포커스 복귀
- 반복 플레이 시 이벤트 및 타이머 중복 여부

## 11.4 UI 데이터

- 점수, 체력, 자원, 진행 상태 등이 실제 데이터와 일치하는가?
- 큰 숫자와 긴 이름에서도 레이아웃이 유지되는가?
- 성공, 실패, 비활성 상태가 명확한가?
- 실제 존재하지 않는 데이터가 표시되지 않는가?

## 11.5 결과 기록

가능하면 변경 전후를 같은 조건으로 비교한다.

- 화면 크기
- 기기 또는 브라우저
- 입력 장치
- 게임 상태
- 스크린샷 또는 재현 단계
- 성공, 실패, 미검증 여부

실행하지 않은 테스트를 통과했다고 기록하지 않는다.
